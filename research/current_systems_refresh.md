## 1. 推荐结论

**ProgressCompass 是当前最值得深入研究的现有系统；R²VLM 是必须认真比较的已发布推理方法；RoboMeter-4B 保留为公开资源较齐全的机器人进展基底。**这三个角色不同，不构成跨基准能力排名。ProgressCompass 尚未发布代码，不能直接承诺原法复现；RoboMeter 的资源可获得也不等于本机已具备运行条件。

## 2. ProgressCompass 为什么值得优先看

它在任务理解、进展估计和完成核验之间建立了明确分工，属于用户希望找到的“已有专用系统”。作者采用冻结 RoboMeter-4B，配 Qwen3.5-27B Orienter、Qwen3.5-9B Verifier 和文本调度器。在其 ContextProgress-Bench 上，完整系统报告 MAE 从 25.4 降至 9.3（0–100 尺度）。这属于特定基准的作者结果，不证明整个领域最强；增加模型、信息组织和调用成本后的结果也不是等预算比较。[论文 §4–5、附录 B](https://arxiv.org/html/2609.36684v1)

最具体的待检点在附录 B：计划可以修改尚未完成的步骤，已确认完成的步骤保持固定。**历史上完成过，与任务要求的成果现在仍有效，需要分开。**对“将物体送出再带回”之类事件序列，保留历史完成记录可能完全正确；对要求堆叠最终成立或持续成立的任务，则应查系统如何表达后续破坏。这是从实现描述提出的假设，尚非实测错误。系统还能描述 lasting state／brief interaction，不能简化为完全不理解两者差别。

其主要基准围绕状态回忆、顺序跟踪和重复事件区分；负例为提前结束、多做步骤与任务不匹配。本轮没有核得专门针对“已达成条件后来失效”的逐例能力结论。不能把论文未专门报告某项实验当作能力失败。

复现与公平性还需保留两点：人工上下文诊断使用标注子任务和边界，附录 C 部分模型的采样设置也变化，不能直接称为完全同输入的纯历史消融；完成候选可取持续下降前峰值，因果在线判断时要核候选确认的时刻，不能仅由 Orienter 不看未来推出整个循环无延迟。

## 3. 为什么不直接选“最新且最高分”的名字

RoboMonitor 在 52 条监督轨迹下的阶段识别强于所比方法，但失败 AP 为 45.87%，低于 RoboMeter + Temporal SFT 的 59.39%；100 条监督轨迹下才在表中四项均值领先。这是额外训练后的对照，不能用来宣布冻结 RoboMeter 已过时。没有确认可用 checkpoint 时，也不能在本项目不训练的约束下直接采用。[Table I、§VI-A](https://arxiv.org/html/2609.30715v1)

R²VLM 已有可演化的步骤状态与历史推理，是反驳“现有系统只会记已完成、不会修正”的重要对照。官方 README 证实权重发布，但尚未完成推理／评测入口与本机资源审核；不能把下载作者微调权重替换为使用本地通用 Qwen，再称原法复现。

另核到 [StageGuard](https://arxiv.org/html/2609.20791v1)，2026-09-17，主要判断技能继续／切换，覆盖更窄；同名 Hugging Face 权重与论文作者、精确实验版本的对应未核定，未列为可直接复现方案。[ROVER](https://rover-vlm.github.io/)（NeurIPS 2025）有公开递归视频推理实现，但现 README 快速示例使用付费模型 API，本轮不运行；它可作历史方法参照，不能替代近期比较。

## 4. 具体下一步

优先对 ProgressCompass 与 R²VLM 做“历史完成／当前仍有效”的原生语义与接口对照：从作者任务及公开示例中各定向找一条需要维持旧成果的执行，核定原输出是否承诺判断该成果仍成立、是否发布对应预测。若只有进展曲线，先确认如何公平关联到任务要求，不能强行按本项目逐条件标签判错。资源未发布的部分明确记录；不把完整复现或先找到作者错例设成提出研究假设的门槛。

ep621／ep618 可继续作为开发现象材料，前者旧绿—蓝关系失效、后者保持仍属单人判断；它们没有变成上述系统的作者错例，也不证明长时程性能。后续如需实测，再固定可用原法、样例、输入权限和预算；目前未下载权重、未运行模型、未新增运行台账。
