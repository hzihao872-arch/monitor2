# 以 RoboMonitor 为研究基底：原生错误、竞争解释与免训练改进边界

检索日期：2026-10-03（Asia/Shanghai）。依据：[研究流程](../PROGRESS_MONITOR_RESEARCH_WORKFLOW.md)。本轮按用户指定，条件性评估 RoboMonitor，复用已有候选筛选，不另凑 3—5 个基底。不把条件评估写成最终立项；不恢复 RoboMeter—ProgressCompass 或 VLAC-Cut—ARS 已停止切口。

## 1. 判断

**可以把 RoboMonitor 作为在线执行监测的诊断基底。最有依据的入口是失败检测的剩余错误；目前适合提出研究问题，还不足以承诺可复现的新架构。**

它满足多输出、多任务、作者原生错误可查的要求，但任务覆盖不等于开放世界通用性。若研究目标必须是连续完成百分比，它与目标并不完全一致。材料开放状态是实际实验的首要限制，不能靠替换成普通 Qwen 来绕过。

推荐的问题表述：

> 在已有执行监测器权重冻结、不使用目标任务标签或成功示范进行适配的条件下，如何利用在线可见证据减少失败事件漏检，并控制误报与报警延迟？

这只是问题，不是贡献声明。其价值不依赖“失败检测从未有人研究”。

## 2. 基底与直接证据

一手来源：[arXiv 元数据](https://arxiv.org/abs/2609.30715)、[正文 v1](https://arxiv.org/html/2609.30715v1)。首次公开及当前查到版本日期均为 2026-09-25。代码、权重、数据发布日期未确认。

RoboMonitor 输入任务指令和因果多相机窗口，输出阶段、失败、完成状态。四个下游任务均参与 SFT；冻结此 checkpoint 做免训练改进，不等于证明基底对这些任务是零样本。论文原生结果提供以下入口，均非本项目复现：

| 证据位置 | 作者报告 | 能支持的判断 |
|---|---|---|
| Table I，52 条标注配置 | RoboMonitor 阶段准确率 93.09%；failure AP 45.87%，同条件 RoboMeter 为 59.39% | 低标注配置的优势未同步体现在失败分数排序上 |
| Table I，100 条配置 | RoboMonitor failure AP 72.01%，高于同表 RoboMeter 的 67.68% | 不能概括成 RoboMonitor 失败检测全面弱；必须保留强配置 |
| Table II，Reel Packing | 18 次失败事件检出 15 次；未观察到错误恢复触发 | 3 次事件漏检是任务级原生证据，零误触发是正确对照 |
| Table II，Toolbox Sorting | 12 次失败事件检出 11 次；未观察到错误恢复触发 | 另有 1 次漏检；跨任务共性仍未知 |

上述事实定位到正文 Table I/II、§V–VI；以下推论和方案属于我们的分析：

- AP 不是召回率，45.87% AP 不能解释成漏检 54.13%。单纯改变某个报警阈值通常不会改变原始分数排序或 AP。
- 18 是失败事件数，不能当作 18 条独立轨迹；事件如何跨 trial 分布未获得。
- 零错误恢复触发不等于已经证明所有窗口都无误报，更不保证新数据上误报率为零。
- Table I 与 Table II 是不同协议；本轮未从正文找到闭环 checkpoint 对应的标注预算、报警阈值和持续判定规则，不能把 3 次漏检归给 52 条配置。
- 未得到这 3 次事件的视频、时间戳和输出。掉落、交接失败、遮挡、停滞都不能写成已确认错例类型。
- 机器人最终任务失败可能包含检测、恢复或控制的问题，不能全部记作监测器漏检。

既有材料：[本地论文 HTML](sources/system_refresh_20261003/robomonitor_v1.html)、[首轮筛选 §6](new_baseline_search_20261003.md)。本轮重新联网核对原文，而非仅沿用旧报告结论。

## 3. 优先区分两种竞争解释

### H1：分数已有信号，但事件报警规则没有有效利用

**解释假说：** 漏检事件可能出现过偏高的失败分数，但幅度、持续时间或触发条件未达到实际报警规则要求。零错误恢复触发与此相容，却不能证明规则过于保守。

**最便宜的区分动作：** 取得原始分数、报警规则及事件时间轴，比较漏检事件、已检出事件、正常执行。先做无需模型重跑的日志回放。

**候选机制边界：** 固定的因果平滑、滞回、持续判定或累计证据可以作简单对照。时间累积本身已有大量工作，不能当新颖性。相邻窗口高度相关，也不能把重复观察当独立证据不断乘概率。

**否定条件：** 漏检事件的分数和正常执行始终重叠，或任何召回改善都只能通过显著增加误报/延迟取得。若简单规则已解决，也应如实接受，而不继续堆模块。

### H2：失败分数缺乏区分，但其他原生输出或可见信息仍有补充证据

**解释假说：** 某些事件中，单独失败分数不足，而阶段轨迹、完成输出或同一输入中的可见变化可能提供互补信息。总体阶段成绩高并不能证明它在这几次失败事件中也答对；这正是需要检验的部分。

**最便宜的区分动作：** 在同一事件时间轴并列三个原生输出和输入可见性，先查是否确实有互补信号，再考虑免训练联合判定或有条件的复核。

**候选机制边界：** 只有发现真实互补性，且简单规则/已有监测法不能充分利用时，才研究具体推理机制。“三个头投票”“加第二个 VLM”不足以构成贡献。不能预设失败与完成必然互斥，也不能认定阶段停留长或退回前阶段必然失败；需先核标签语义及合法恢复行为。

**否定条件：** 三种输出在漏检时同时失去有效信息，或所谓互补依赖真实当前子任务、未来帧、任务示范或额外传感器。若证据确实在输入外，只能研究新增信息条件，并明确它改变了设定。

两种解释都尚未确诊；稀有失败监督不足、分布差异、标签边界和视觉遮挡是其他竞争解释。当前不把“缺历史”“平滑压掉异常”写成结论。

## 4. 查重结果与继续条件

以下按机制比较，跨论文数值不作横向排名。

| 一手来源 | 已有机制与条件 | 对本方向的限制 |
|---|---|---|
| [Sentinel，§4、附录 A/B](https://arxiv.org/html/2410.04640v2) | 时间动作一致性累积与 VLM 进展监测互补；STAC 使用成功 rollout 校准 | “快慢双监测”“累积异常”“互补检测器”均不能重新命名成创新。原法动作访问及校准条件需单列；无参数训练不等于无任务适配 |
| [DoReMi，§3](https://arxiv.org/html/2307.00329v3) | LLM 为计划步骤生成约束，VLM 持续检查违反情况 | “阶段相关条件＋持续检查”重合明显。RoboMonitor 不给真实当前子任务；公平比较要区分预测阶段和规划器提供的阶段 |
| [Code-as-Monitor，§3](https://arxiv.org/html/2412.04455v2) | VLM 生成代码检查时空约束，利用可跟踪的几何元素；涉及深度和三维信息 | 不能泛称“视觉验证新架构”。移除深度后的 RGB 版本属于适配版，不能冒充原论文方法 |
| [SafeContract，§II](https://arxiv.org/html/2605.28726v1) | 以动作流为对象，结合 conformal 校准和 CUSUM | 顺序证据与变化检测已有方法；改为视觉监测分数不自动形成新贡献。本文只将其作机制检索命中，不采用未经独立审查的理论保证 |
| [Guardian，§4.3、§5](https://arxiv.org/html/2512.01946v4) | 训练多视角子任务验证和推理模型 | 失败视觉证据与复核有训练型强法。冻结公开模型可成为辅助比较，但要报告模型规模、输入、子任务条件和额外调用 |
| [Foresight，§1、方法与实验](https://arxiv.org/html/2606.23085v1) | 训练动作条件预测器，利用任务结果标签及阈值校准 | “用历史/预测表征提高失败检测”并非空白；不属于本轮无需新增训练的方案 |

RoboMonitor 本身已经使用时间上下文和时间一致性训练。因此不能以“第一次考虑时间关系”作为动机。其结论也讨论多标签状态、语言解释及不确定性方向；作者列出的未来工作可以研究，但不是未经研究的新领域。

**查重结论：** 尚未确认能直接解决 RoboMonitor 上述原生错误、且满足本项目全部条件的现成方法；也没有得到可声称新颖的具体机制。继续的理由是原生错误存在、诊断可区分；不是模型发布不久或引用少。

最小材料请求清单（未联系作者）：

1. 与 Table I/II 对应的 checkpoint 标识及推理配置；若尚不开放权重，先提供保存的原生输出即可开展 H1 的初步诊断。
2. 失败事件标注、时间戳、报警记录及触发规则；说明一次失败如何被统计为检出。
3. 同轨阶段/失败/完成输出，包含正常、正确检测和漏检案例；视频及采样坐标供核可见性。

拿不到原始输出时，可以继续提出和讨论问题，但不能报告“已复现”“已减少漏检”或用其他 VLM 替代 RoboMonitor 的成绩。也不为此重新从头训练 RoboMonitor。

## 6. 最小诊断和公平验证

先覆盖可追踪漏检，再配同任务已检出失败与正常执行，尤其保留合法等待、纠正和阶段切换对照；不存在的样本不预先编数。来自同一 episode 的窗口、不同视角和事件必须绑定同一组。

第一轮只比较原生报警与固定的简单因果规则，回答 H1。若只拿到输出日志，暂不能声称完成 H2 的视觉诊断。看过标签用于选择机制的材料全部为开发集。

如果出现可利用的补充信息，再比较：失败分数单独使用、其他输出单独使用、简单联合规则、最接近已有法的同条件版本、候选机制。若调用辅助 VLM，加辅助模型单独运行和相同调用预算对照，防止把更大模型收益写成架构收益。

核心指标同时包含事件检出率、每 episode 错误报警/错误恢复触发、相对可见失败起点的延迟；失败 AP 作为排序指标另报。检查对原有阶段与完成能力的损伤。闭环任务成功率以后再验证，不代替监测器指标。

无目标标签适配是主设定：可以报告完整阈值曲线作诊断，却不能从目标测试标签选最佳阈值并冒称 zero-shot。需要标注校准的已有方法单列条件。小开发集上的“未增加误报”不提供总体零误报保证。

## 7. 给老师的汇报稿

> 我想以 RoboMonitor 为在线执行监测基底。作者结果已提供失败检测的剩余错误，但目前不能把它归因于缺少历史或视觉理解不足。我计划先用原生输出区分：失败信息已经在分数中、只是报警规则未有效利用，还是需要其他输出或可见证据补充。Sentinel、DoReMi 和 Code-as-Monitor 已覆盖累积监测、互补检测和约束检查，因此不会把这些宽泛机制当作创新。若诊断发现现有简单方法不能解决、又能在冻结权重及无目标标签适配条件下利用的证据，再研究具体架构。目前最实际的前提是取得与原结果对应的输出日志或 checkpoint。
