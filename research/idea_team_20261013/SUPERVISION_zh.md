# 监督来源账本：有哪些真信号，哪些仍然要付成本

2026-10-13。本文是研究设计账本，不是已生成的数据集或已运行的管线。主推荐见[PROPOSAL_zh.md](PROPOSAL_zh.md)。

## 先回答“大量标签从哪里来”

这轮不再以大量成对续行标签作为必要前提。设想是少量初始条件标签，加执行中自然到达的局部证据；只训练可以独立证实的一小部分条件/区间。**省的是逐帧进度解释和每状态反事实分支；不是省掉真实执行、标注者判断和独立证据。**

不会承诺少量事件足以泛化。一个使用事件传播到50帧，仍主要是一份物理证据。统计和划分按事件/原轨迹/场景，标签扩展倍数与独立证据数量分开报告。

## 一条合格监督记录应该长什么样

| 字段 | 含义与来源 |
|---|---|
| episode、prefix_end | 实际轨迹身份和允许学生读取的截止时刻 |
| goal、task_family | 已给定的最终目标；任务族的条件语义需少量人工定义 |
| condition、entities | 明确关系，如指定刚体对指定入口的通行条件；谁是目标物/支撑部件须核查 |
| physical_scope | 物体规格、相关几何、载荷、放置配置等该条件依赖的变量；不是泛泛“可完成” |
| witness_time、evidence | 真实通过/释放稳定/直接封堵证据；来自外部记录或审核者 |
| valid_interval | 独立核查可支持的有限区间；不知道就只留事件帧 |
| label、supervision_mask | 成立或直接否证；没有证据的位置不训练。unknown不等于false |
| required_now | 单独的任务阶段义务标签；少量人工模板与独立局部使用/完成事件决定。完整入盒后可解除入口义务，即使尚待释放；支撑义务持续到稳定合同结束。不从终局成功广播，不由学生阶段自评批准 |
| review_time、reviewer、reason | 审核成本、来源与拒收原因；用于和直接标状态做公平比较 |

模型自身的解释、概率、世界模型想象和未审核编辑图可以进入“待核查”字段，不能进入独立truth字段。

## 第一个入口例子：确实通过，而不是盖动了

第一版条件定义为“这个刚体在该入口的相关碰撞几何约束下存在通行配置”。后来实际通过的姿态/轨迹提供一个存在性见证，不是学生必须猜的未来路径；若进入时盖被推开，只能证明推开后的几何，不能回推原先的封闭状态。

要监督更早的画面，至少须核查对象身份与规格、入口相关几何和妨碍通行的有关环境关系。仅看盖板位置没变，不足以证明整个通道没变。若条件定义改成“这个夹爪按当前固定路线能放进去”，则一次别的姿态/路径通过不能监督它；第一版不学习这个较强结论。

负监督可来自唯一入口净空小于刚体沿相关轴的最小宽度，而且没有其他合法通道的独立几何证据。这只能否证对应当前通行条件，不证明机器人永远无法完成任务——它可能以后开盖。

## 第二个承载例子：谁在承托、持续了多久

释放、指定面接触、没有夹爪或其他支撑、速度与位移在合同窗口内，才支持指定任务的稳定证据。当前合同至少0.5秒，不能说永久稳定。

向放置前传播“可承载”证据，还需核查相同载荷、结构和放置配置的假设。隐藏支撑、材料变化、不同载荷、不同姿态或放置位置都可使传播失效。无法核查时，退回“这次实际放置稳定”的事件标签。

一般“掉落”不证明承载条件为假：可能放偏、夹爪碰撞或姿态不同。负标签优先来自独立确认目标区域没有任何合格支撑的直接证据；普通任务失败留下未知。平台移动首先只使旧证据失效，撤掉掩码，并不自动成为负标签。实际失稳只否定当次配置/窗口。对任务完成判断则可使用独立终局合同，仍不能把它变成全阶段的成功标签。

## 第一份监督具体怎样起步

未来最小管线设计：人工先定义一个通行条件和一个承载条件；读现有truth记录定位合格事件与直接反证，逐项注明证据类型；完整仿真状态直接算标签，不绕回溯；人核查图像能否表现这些条件，把遮挡和语义不匹配样本剔除。由此取得第一份有来源的开发监督，但不宣称泛化。

再选一小批新真实或外部片段。给审核者看完整局部视频，让其确认事件及最近可信变化点，并记录时间；区间不确定就只点证据帧。作为对照，另一组相同分钟预算直接标条件状态。20–40个独立单元只能作为管线和成本试做示例，数量既没有做过power计算，也不是足够训练的承诺。

参数学习可以先更新小条件头；后续新反馈只加入合格标签，不能因Monitor更自信就扩大自己的truth集合。当前没有运行以上任何步骤。

## 备选D的标签为何逻辑更干净，资源却不确定

一条反例证书需要：

1. 在起始状态，目标尚未完成，任务对象相同。
2. 明确Monitor的声明是“在该环境与允许动作/预算下，任何完成方式都必须满足c”，不是仅“下一技能需要c”。
3. 允许的实际执行全程没有满足c，absence有完整记录或人工可核查证据；仅抽几帧不够。
4. 最终目标经独立合同或审核确实完成，成功在预算内。

它只给“c不是这个任务设置下的普遍必要条件”的单向监督。没有发生反例就保持未知；失败也不证明c必要。真实必要条件须由独立几何约束、人工任务合同等给初始锚点，不能从所有成功样本都做过某事就推导必需。

当前唯一顶入口没有这种替代路证书。之后可另设计双入口或替代支撑的任务并采少量完成片段，但要付场景/路线/执行成本；从公开play挑选也要验证完整absence，不能把这一步写成无成本。经典[成功前状态交集](https://www.ijcai.org/Proceedings/2017/0615.pdf)与[反例修复](https://arxiv.org/html/2105.06537v1)是必须比较的简单机制。

## 何时必须承认做不下去

如果真实证据太少、对象/状态日志缺失，或确认有效区间比直接标状态更费时，主推荐的省监督依据就不成立。若只有现有完整oracle仿真，直接条件SFT更自然；不为保留论文故事人为丢状态。若想恢复全任务帮助/有害/价值概率，则需要额外的关系语义、替代路线或后果监督，本账本不声称已经免费解决。
