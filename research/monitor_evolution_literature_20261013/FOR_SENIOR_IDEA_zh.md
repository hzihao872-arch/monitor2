# 执行反馈驱动的任务 Monitor 改进思路

讨论稿｜2026 年 10 月 13 日

师姐，我把最近几轮找到的相关工作放在一起梳理了一下。目前想把研究问题收紧到：**如何把执行中的物理反馈转成适用范围明确的监督，持续改进任务 Monitor，让它更准确地判断任务推进、前置条件受阻，以及已有成果失效。**

RoboMonitor 可以提供时序 Monitor 的训练基底，StageGuard 是阶段决策上的直接对照，Reflective Test-Time Planning 和四足持续学习工作则提供反馈关联、事后修正与模型更新的思路。我想在这些工作的基础上，先验证一个具体机制是否有效，再确定创新点能够成立到什么程度。以下是当前方案，尚未开展这份方案的实验。

## 1. 我现在想研究的问题

执行过程中的反馈常常是局部、延迟且有条件的。例如，方块成功通过入口，可以证明这次通过确实发生；但它是否还能监督通过前的“入口可通行”判断，取决于对象、路线、入口配置及其变化。一次失败也可能来自控制误差，不能直接把相关条件标成不成立。

因此，我想研究的核心链条是：

> 可核验的执行反馈 → 明确它支持的命题和时间范围 → 构造可靠监督 → 更新 Monitor → 在新的执行中判断任务进退。

这里的候选贡献是**执行证据到任务监督的转化机制**，需要回答三个问题：

1. **反馈证明了什么？** 是动作尝试失败、某个物理条件不成立，还是一个任务成果已经达成？
2. **反馈能监督哪些观测？** 它对应哪个对象、哪组配置、哪个时间区间；遇到状态变化或遮挡时，应在哪里停止关联？
3. **这个事实对后续任务还有什么作用？** 当前条件失效可能阻碍下一步，也可能已经无关；已有成果失效则可能要求恢复。

“收集执行数据再训练 Monitor”已有先例；增加几个状态输出也不足以单独构成创新。我希望检验的是：**在相同反馈与核验成本下，这种监督机制是否比直接纠错或固定窗口标注更可靠，并带来后续监测收益。**

## 2. 用入口开关和平台支撑说明整个流程

先明确任务约定：红方块经过指定入口进入目标区域，释放后由指定平台稳定支撑达到规定时间，并保持到本轮结束。对象、允许的通过方式、平台和保持要求都要写清楚，避免标签含义漂移。

### 入口开关

假设入口经历“开启 → 关闭 → 重新开启 → 方块实际通过”。完整通过是一个正向证据，首先确认“这个方块已经通过指定入口”。

如果要进一步监督通过前的可通行判断，只能在相关配置经过核验、确实保持一致的范围内关联历史观测。不能跨越关闭再开启的变化，把后面的成功直接传播到更早的整个阶段。如果通过过程中入口本身在运动，这次动态通过也不能直接证明某个静态画面的可通行性。

相反，一次碰撞或超时不能直接形成“入口不可通行”的负标签。需要区分控制失败和物理条件不满足；几何约束、传感器或独立人工核验可以提供更可靠的依据。按下开关本身也不等于入口实际具备通过条件。

### 平台支撑

假设方块经历“抓手托持 → 释放 → 摇晃 → 稳定支撑”。正标签应从已核验满足支撑要求的区间开始，不能提前覆盖抓手仍托着或尚未稳定的时刻。还要确认支撑来自指定平台，而非其他物体。

如果之后平台移走，可靠观察到支撑要求被破坏，就应将当前成果判为失效。如果只是发生遮挡，则保留为未知，不能据此标成失败。

### 最后如何判断任务进退

需要分别维护以下信息：

| 信息 | 含义 | 例子 |
|---|---|---|
| 当前条件 | 现在是否满足某项物理条件 | 入口现在是否允许该方块通过 |
| 历史达成 | 某个里程碑是否曾经完成 | 方块已经通过入口 |
| 当前成果有效性 | 已达成结果现在是否仍满足要求 | 指定平台仍稳定支撑方块 |
| 剩余义务 | 后续任务是否还需要某项条件或成果 | 是否还要使用入口，支撑是否必须保持 |

由此得到三种不同判断：

- **尚未通过，入口不可通行：** 前置条件受阻，需要恢复入口条件。
- **已经通过，入口关闭，后续不再使用入口：** 已有进展仍成立，不应退回通过前的阶段。
- **放置完成后，要求保持的支撑失效：** 历史放置仍然发生过，但当前成果需要恢复。

这些区分构成任务接口。真正要检验的，是执行反馈构造的监督能否让 Monitor 在新轨迹中更准确地识别这些情况。

## 3. 相关论文分别提供什么

### RoboMonitor：训练基底与低标注对照

[RoboMonitor](https://arxiv.org/abs/2609.30715) 的主要贡献是预测式表示学习和因果时序监督，用较少监测标注学习阶段、失败与完成判断。它的主要创新确实不是通过部署执行反馈生成新标签。

可以借鉴因果时序输入、窗口内多个位置的监督、重叠窗口一致性以及失败样本加权。需要注意，一致性约束不能把真实的关闭、掉落或成果失效平滑掉，也不能替代标签核验。

我们的候选区别在于监督如何从执行证据产生、适用范围如何界定。低标注 Monitor 与时序训练部分仍有共同点，不能笼统地认为完全不重合。

### StageGuard：同一类阶段决策问题的直接对照

[StageGuard](https://arxiv.org/abs/2609.20791) 利用已有阶段真值组织教师推理，再蒸馏成执行时的阶段决策模型，判断继续、推进或跳过。

可以借鉴它的“状态证据 → 任务关系 → 决策”组织方式，以及简洁的解释和结构化输出。但教师解释主要用于组织监督；真值不能仅由教师自洽或教师之间一致来确认。

它与我们是同一类问题的不同路线，需要作为核心对照。我们的重点是执行证据如何产生任务条件及成果有效性的监督，而其重点是阶段决策蒸馏。区别必须通过共同测试情形体现，不能仅靠改输出名称，也不能预设它无法处理动态变化。

### Reflective Test-Time Planning：反馈修正与监督更新的对照

[Learning from Trials and Errors: Reflective Test-Time Planning for Embodied LLMs](https://arxiv.org/abs/2602.21198) 在执行后获得反馈，并通过后续回顾修正早期评估；它同时更新内部动作评估模型和动作策略。

因此，“我们重训练 Monitor”不足以作为区别。更具体的比较应是：它侧重候选动作的评估与规划改进；我们拟学习当前任务事实、成果有效性及其对剩余任务的作用，并明确监督的物理依据和适用范围。

可以借鉴即时反馈与延迟反馈分开、后续核验修正早期标签、记录反馈版本及来源的方式。初版固定策略，是为了分析 Monitor 的收益来源，本身不是创新点。

### 四足持续学习：物理反馈关联与更新管理的思路借鉴

[Experience-Driven Continual Learning of Terrain Traversability for Quadruped Robots](https://arxiv.org/abs/2609.39755) 将接触反馈关联到此前视觉观测，用于持续改进可通行性预测。

可以借鉴反馈与观测匹配、缺失及置信度处理、新旧数据回放、模型更新验证门槛。我们不能把这些闭环做法本身当作新贡献；需要进一步研究操作任务中，对象与环境配置变化如何限制监督范围，以及条件变化如何影响任务进退。

### Sirius-Fleet：部署反馈学习的历史基线

[Multi-Task Interactive Robot Fleet Learning with Visual World Models（Sirius-Fleet）](https://arxiv.org/abs/2410.22689) 已经利用部署与人类干预数据，迭代改进失败检测和机器人策略。

它说明“执行反馈 → 更新检测器”的闭环已有操作机器人领域先例。可以借鉴分轮学习流程，并作为反馈学习对照。人类干预或风险标签与物理条件真值含义不同，因此比较时需要明确标签和任务接口；适配后的基线也要注明改动。

此外，[ConditionNET](https://arxiv.org/abs/2502.01167) 已研究前置条件与动作效果监测，[ARS](https://arxiv.org/abs/2609.34484) 涉及证据核验、任务进展及退步判断。它们提醒我们：条件监测和任务退步都不能直接作为“首次提出”的贡献；可以借鉴任务条件定义和证据确认、失效记录的设计。

## 4. 我倾向的初版架构

初版采用一个因果时序 Monitor，加上明确的任务状态记录和监督生成流程：

```text
执行时：
任务约定 + 截至当前的观测
    → 因果时序 Monitor
    → 更新任务状态记录
    → 判断推进 / 受阻 / 成果失效 / 未知

模型更新时：
执行结果 + 后续核验
    → 记录证据及其对象、配置、时间范围
    → 构造已核验标签，未知位置不参与监督
    → 混合新旧数据训练
    → 验证新场景收益和旧任务保持
    → 决定是否采用新 Monitor
```

实现选择上，我想先控制复杂度：

1. **任务约定先明确给定。** 初版用简单任务依赖和事件记录维护历史达成、剩余义务，暂不同时研究自动任务分解。
2. **学生严格使用历史观测。** 后续执行结果可以帮助构造过去时刻的训练标签，但过去时刻的模型输入不能包含后续画面、解释或结果摘要。
3. **先更新小型时序模块。** 借鉴 RoboMonitor 的监督方式，先判断标签机制是否有效，再决定是否需要扩大微调范围或增加预训练。
4. **教师负责整理，核验负责提供依据。** 借鉴 StageGuard 的推理结构和 RTTP 的回顾修正，保留未知与标签版本；不把生成解释视为独立物理证据。
5. **新旧数据共同约束更新。** 借鉴四足工作的回放和更新验证思路，避免只改善新场景、损害原有任务。

这里有两个更新过程：执行时更新任务状态，积累监督后更新模型参数。二者需要分别评估。

## 5. 最小实验准备验证什么

我想先验证一个假设：

> 在相同学生模型、任务状态接口和总反馈核验预算下，按对象、配置变化及证据有效范围构造监督，比直接纠错或固定时间窗口标注，更能改善新轨迹上的受阻与成果失效判断。

最小比较包括：

| 组别 | 监督构造方式 | 要检验的作用 |
|---|---|---|
| 直接标注 | 对关键事件或错误位置进行核验和标注 | 可靠纠错本身能带来多少收益 |
| 固定窗口 | 将事件标签关联到固定长度的历史窗口 | 简单扩展监督是否已经足够 |
| 证据范围 | 根据对象、配置变化和核验结果选择监督位置 | 明确适用范围是否有额外价值 |

三组采用相同学生、训练设置和任务状态记录。预算应包含反馈采集、人工检查和范围核验的总成本；测试集按场景、配置及轨迹划分，避免相邻帧泄漏。新模型应在后续或独立轨迹上评估，不能用事后标签修正已经输出的在线预测，再据此计算收益。

重点测试：通过后关门是否被误判成任务退步；放置后支撑失效是否被漏判；遮挡是否被误判成失败；单次控制失败是否污染条件标签。同时记录监督错误率、有效标签覆盖、总核验时间和旧任务表现。

如果固定窗口或直接标注取得相近效果，或者范围核验的成本抵消收益，就需要收缩这条机制的贡献。最终应以“同样成本获得更有用的监督，并改善后续判断”作为依据，而非标签数量增加或架构更复杂。

## 6. 想和师姐重点讨论的取舍

我目前倾向于把**证据到监督的转化**作为主线，把时序训练、任务状态记录和更新管理作为支撑。解释蒸馏可作为辅助或对照；联合更新策略与评估器更接近 RTTP，适合在 Monitor 的独立收益明确后再展开。

想重点讨论三个问题：

- 这个问题是否足够独立，还是更适合定位为现有 Monitor 的监督构造与评测扩展？
- 第一版应聚焦一个判断难点，例如持续支撑成果的失效，还是同时覆盖入口前置条件与平台成果有效性？
- 最优先的强对照，应是 StageGuard 式阶段决策蒸馏，还是相同学生下的直接人工纠错与固定窗口监督？

现阶段先将其定位为**执行反馈驱动的监督式持续改进**。创新程度取决于后续机制设计与对照结果，暂不主张递归自改进或更强的自主能力。
