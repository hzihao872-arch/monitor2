# 剩余服务器时间的研究决策与修订运行顺序

日期：2026-10-07。用户确认实例目前**关机**；本文件仅完成本地设计，尚未连接或运行 P4/P5/P6。原 [P4/P5 方案](TAIL_WINDOW_P4_PLAN.md)、[运行卡](RUN_NEXT_SERVER_zh.md) 和已冻结输入包保留，不覆盖其证据。新增 P6 详见 [独立设计](P6_DIRECT_BASELINE_PLAN_zh.md)。

## 1. 当前结论与真正需要回答的问题

现有开发证据已足以支持研究立题：TOPReward 对有效准备 E 的六个预定配对均未排对，Robometer 在入口盒的三对中有两对失配、在承托板三对全对；实际完成 G 对照均响应，相同输入重跑结果稳定。下一步不应再靠同样输入重复证明“有问题”，而应判断**哪一种低成本方法可能改善有效准备、无效/无关动作与撤销进度的区分**。正式跨场景效力仍留给 G2。

## 2. 新增 P6 与预制 P4/P5 的取舍

| 诊断 | 可回答的问题 | 解释边界 | 本次优先级 |
| --- | --- | --- | --- |
| P6 direct：18 次无结构提示直接问答 | 同一基础 8B 只凭目标和视频，简单直接提问能否区分有效、无效、有害及已完成 | 另行提示的基础模型，不是 TOPReward/Robometer 内部状态；只测 t0→t14 净变化 | 1 |
| P5 visual：18 次定点视觉问答 | 指向关键结构后，基础 8B 能否辨认开口/承托的初、中、末状态 | 提示已经点名结构，不能证明自动发现相关对象；不是原生评分器内部读出 | 2 |
| P5 necessity：18 次从 t14 续行问答 | 明确时间起点后，基础 8B 能否区分已完成、可继续完成与受阻 | 提示已给动作限制；与 visual 独立起问，结果只能提示排查方向，不能严格定位单一瓶颈 | 3 |
| P4 neutral + causal_fact：各 18 次 TOPReward | 普通准备提醒与明确前置关系文字能否改变原生分数排序 | 改变了目标文字，长度/措辞也不同；只能作提示敏感性诊断，不能当原始输入协议或 G2 成绩 | 4、5，作为一组解释 |
| P4 credit_rule：18 次 TOPReward | 直接写明“准备也算进展”是否强行改变排序 | 接近提供评分规则，若有效仍不足以表明模型自主识别有用准备 | 默认跳过；仅在上述结果已安全下载且租期充裕时运行 |

因此，**不照原卡的 P4 全部三变体 → P5 顺序执行**。P6 是额外独立冻结实验；P4/P5 原远程脚本把 P5 visual 强制依赖 `credit_rule` 已验封，本地另存的 `run_remote_p4_p5_reviewed.sh` 只调整这一依赖，保留 P4/P5 模型代码包、匿名视频、提示、权重及封存方式。它要求 P5 necessity 在 P5 visual 本地验封后启动；P4 causal_fact 在 P4 neutral 本地验封后启动。`credit_rule` 可选且仍须在 causal_fact 验封后启动。原脚本不改。

## 3. 开机前和租期内的执行规则

1. 开机前确认仍为用户已租实例；开机后从服务商读取**实际到期时间及 SSH 端点**，不沿用旧的 12:40 UTC 保守截止。若 P0 远端目录或模型身份不符，停止新的诊断；已下载的 P0–P3 不受影响。
2. 上传新增 `p6_model_code.zip`、`run_remote_p6.sh`，以及既有 `p4_p5_upload.zip`、新 `run_remote_p4_p5_reviewed.sh`。P6 代码 ZIP SHA-256 为 `27aacffe5588b043e3d582eba30458eca420a6ccb068c1b282e5b81cf3e3d736`；P6 shell SHA-256 为 `abaccceacab069b9d5d179bffbac1557b56b37601e6d26735b0622b24814426f`。P4/P5 ZIP SHA-256 为 `d9fe7ba669d5f9362facae95fbeb2882ec42d565261dcf7c00491119377e070c`；修订 shell SHA-256 为 `456f6e9bf63f2479577d3e1e989146ff28f91cbc4ae715aa0e1aa4579b4da987`。上传包均不含真值、条件映射、评分器或旧分数。
3. 按 `p6-direct → p5-visual → p5-necessity → p4-neutral → p4-causal_fact` 固定顺序，每项先按远程脚本的资源、版本、哈希、余时检查和 pilot 执行。P6 远端封存后立即运行 `collect_p6.ps1`；其余各项运行原 `collect_p4_p5.ps1 -Task <任务名>` 下载并本地验封，收到 Verified 才启动下一项。不要看早期结果后改提示或改变此顺序。
4. 每项启动前至少满足“预计完整运行时间 + 600 秒下载/核验缓冲”。原脚本对 P5 每阶段初始估算 600 秒、P4 每变体 480 秒，并在 pilot 后复核余时。这只是保守计划数；必须记录实际 pilot、加载、传输时间并据此判断下一项。最后十分钟不启动 GPU 单元。任何步骤不足时停止，保留已完成项；不为了凑满调用数牺牲下载。
5. `credit_rule` 默认不列入必跑序列。仅在四项均已本地验封、实际租期仍足够时，可以按预制冻结文本执行。若跳过，报告“未运行”，不补其他临时提示。
6. P6 完整验封后用本地 `score_p6_direct.py` 揭盲，并人工核查理由及引用帧。P5 两阶段均完成后再用本地 `score_p5.py` 揭盲；P4 每变体封存下载后可用 `score_p4.py` 与 P0 比较。全部原答、失败、控制项和九段逐点曲线保留。P5 单阶段完成时仅作对应阶段的原答审读，不冒充两阶段定位结论。

实际 SSH 与收集方式沿用 [原运行卡](RUN_NEXT_SERVER_zh.md)。先把 P6 两文件上传到 `$RUN/incoming/`，执行 `bash "$RUN/incoming/run_remote_p6.sh" <实际到期UTC>`，在本机运行 `collect_p6.ps1`；随后 P4/P5 上传的 shell 文件名以及远程 `bash` 调用改为 `run_remote_p4_p5_reviewed.sh`。密码仅交互输入，不写入文件。任何新的权重下载、实例租赁或原生代码修改均不在本计划内。

## 4. 结果如何转化为方法决策

- P6 在 E/H/G 和无效、无关对照上基本正确：优先把这一简单提问作为候选基线，不为复杂架构而复杂化；随后检验新场景与时序撤销。
- P6 失配但 P5 定点正确：相关结构的自主发现、证据区域选择和任务表述成为优先候选问题。
- P5 视觉状态经逐帧人工核查仍错：先研究关键区域定位、回看与视角可见性；不要把错误归给价值映射。
- P5 视觉状态正确而续行答案仍错：优先研究从当前状态到合法目标的路线/替代路线检查；由于两问独立，仍需后续受控试验确认这一归因。
- P5 两问均正确：说明定点提示下基础 8B 具有候选能力；下一版方法要解决**从仅有最终目标和视频自动提出相关结构、核查状态、将其映射成可撤销的进度**。简单定点问答须作为同预算基线。
- P4 neutral 已改善 E 排序：优先测试低成本任务框架提示，不急于设计复杂结构。
- P4 neutral 未改善、causal_fact 改善：自动发现和表达目标前置关系可能是关键设计点；还需在新场景排除措辞与长度影响。
- P4 两者均不改善：继续开发独立于 TOPReward 原生读出的进度器，避免假定原生分数只靠补一句关系即可修复。

下一阶段应先在现有开发材料上提出**一项最小方法**：由目标和视频提出可能的必要状态，核对相关画面及前后变化，判断该状态是否让目标可继续完成，再给正/零/负/未知进度；开放后关闭时撤销信用。实现不能写死盒盖、黄板、颜色或坐标。与同预算直接提示、Robometer、TOPReward 全条件比较，保留 Robometer 承托板正确的反例。方法稳定后再冻结未见 G2，避免无限追加同一批开发视频诊断。
