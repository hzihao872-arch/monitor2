# 从 EvoNav 提炼的研究流程与本项目适用边界

日期：2026-10-02。阶段 2 产出。依据：[阶段 1 论证图](02_evonav_argument_map.md)与[核验来源](01_evonav_source_record.md)。以下是研究和验证动作，不是算法规格；所有对本项目的建议均标为“我们的解释/补充”，尚无本项目实测结果。

## 1. 值得借鉴的论证组织

**我们的解释**：EvoNav 的可借鉴之处，是把一个判断失误问题连接到设计理由，再把系统比较、局部干预、不同使用条件与成本串成证据链。具体实验的局限也提醒我们：链条的存在不等于每一环都已证实。这是从论文文本重构出的论证逻辑，不是作者研发时间表。

```mermaid
flowchart LR
  A[明确任务和失败问题] --> B[提出可检验的设计理由]
  B --> C[同条件比较整体效果]
  C --> D[干预以检查组件与解释]
  D --> E[跨条件、成本与失败审查]
  E --> F[限定可支持的贡献]
```

此图只表示研究活动，不表示本项目的信息流或模块。

## 3. 本项目必须另加的检查

下列均为**我们的补充**，来自本项目固定问题及 EvoNav 的证据边界，不能归因给 EvoNav 已完成。

| 补充检查 | 为什么需要 | 在后续哪个阶段落实 | 可审查产物 |
|---|---|---|---|
| 区分曾经达成与目前仍成立 | 已做过不等于当前仍有效；导航成功率不是此类监测真值 | 阶段 3 | 时间轴上的要求、当前状态、可见证据与失效时刻定义 |
| 正常调整和真实退步配对 | 检出更多异常可能只是误撤销更多正确进展 | 阶段 3、6 | 仅改变关键关系的案例对；错误确认与错误撤销同时评估 |
| 未知与失败分开 | 遮挡或缺观察不能强制判成失败；一律未知也不是进步 | 阶段 3、6 | 可判断性标签、覆盖率与已判断错误率 |
| 对准最早可观察时刻 | 参考真值可来自全视频，但监测器不能提前知道不可见失效 | 阶段 3、6 | 事件发生时间、首次可观察时间、首次判断时间分列 |
| 强基线与预算对照 | 系统改善不一定说明组织方式不可替代 | 阶段 4–6 | 经文献核验的比较对象及证据/资源权限表；合理开发预算 |
| 直接测量关键判断质量 | 最终任务成功可能由导航或控制改善造成，不能替代监测指标 | 阶段 3、6 | 独立标注的判断目标与指标分母，不以模型自评代替真值 |
| 划分与统计考虑轨迹相关性 | 帧级独立假设会夸大样本量；持续历史还会产生序列依赖 | 阶段 6–8 | 任务/场景级划分、配对比较及按适当独立单位计算的不确定性 |
| 提前写否定条件与停止规则 | 防止看结果后改故事，或用不断叠模块掩盖负结果 | 阶段 5–8 | 假说—反证—决策记录；保留全部先导尝试 |

## 4. 进入架构探索前必须回答的问题

这些是待回答的问题，不是现在要用户逐项确认的表单，也不表示本轮已选定任何方案。

1. 我们的判断对象是某个要求当前是否成立、当前动作是否构成有效推进，还是整体完成？各自允许什么输出，何时只能说未知？
2. 什么具体轨迹能区分“局部成功且总体仍有效”和“局部成功但破坏其他要求”？改变哪一个事件能构成可靠反例？
3. 什么视觉变化在正常调整和真正退步中相同，哪条额外证据才能区分？如果没有这条证据，正确行为是什么？
4. 改善是否来自更准的判断，还是更少肯定/更多未知？错误确认减少时，错误撤销是否上升？
5. 不改变模型权重的前提下，相关工作能否已经解决这些错误？强基线是否足够，剩余差距在哪里？
6. 如果方法看到更多历史、更多图像或得到后验标签，收益应叫信息收益、适应收益还是判断机制收益？怎样通过对照区分？
7. 中间预测或自我反思错误时，系统会如何表现？怎样在实验中区分对错误预测的依赖和独立观察的支持？此问题不预定必须有预测模块。
8. 若候选含多个部分，哪些必要性、互补性或交互主张真的值得检验？哪些只是系统集成选择？
9. 对简单任务、保持条件无关、遮挡或历史丢失等不利情况，复杂过程是否造成代价或新错误？
10. 哪项结果足以让我们简化或放弃候选，而不是继续叠加功能？

## 5. 阶段 3 的具体入口

**下一次工作的第一项动作**：依据[正式计划第七节](../docs/plans/2026-10-02-task-progress-research-plan.md)，创建 `research/04_problem_and_cases.md`，先形成“判断对象—判定条件—需要的证据”表。若没有现成轨迹，先写明确标注的概念案例，不能说已测得现有方法失败。

建议的记录字段属于任务/标注规范，不规定系统内部结构：

| 字段 | 要解决的问题 |
|---|---|
| 案例来源与类型 | 实测轨迹还是概念示例，能否追溯 |
| 用户明确要求与暂定解释 | 避免把推断当用户要求，不能迎合观察放宽要求 |
| 截至 t 的可见观察及允许元数据 | 当前模型究竟能知道什么 |
| 历史已达成事件与当前条件 | 曾经成立和当前仍有效是否分开标注 |
| 参考状态、未知原因 | 真值依据是什么、哪些仍不可判断 |
| 事件发生与最早可观察时刻 | 检测延迟从何时开始合理 |
| 最小变化的配对反例 | 能否排除外观、步骤数或执行速度的混杂 |
| 错误类型及反向代价 | 改善会不会只换成另一种错误 |

初始覆盖应包括正常推进、慢速但有效、必要调整、局部成功伴随条件失效、无效重复和观察不足。数量取决于能否区分核心问题，本轮不提前规定数据集或样本规模。先完成错误定义和案例，随后阶段 4 检索相关研究，阶段 5 才形成可证伪假说与候选架构。

## 6. 边界自查与验收

- **已固定**：冻结模型方向、有效进展与进展失效问题、EvoNav 仅作研究流程参照。
- **仍未固定**：四步闭环、竞争解释、检索、依赖图、任何模块数/调用次序、数据集、模型、指标实现及预算。
- 每项 L1–L10 都是研究动作，有原文依据、目的、前提、调整和不能推出的结论；原文未做的验证单列为我们的补充。
- 没有创建本项目架构或算法代码，没有实验结果，没有创新性或投稿水平结论。
- 阶段 2 的用途是帮助下一步做可判断案例与公平验证；本次到此结束，不自动执行阶段 3。
